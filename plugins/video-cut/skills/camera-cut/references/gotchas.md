# ffmpeg 剪接的坑

全部都是实测踩出来的，不是从文件抄的。改 `scripts/` 之前先读。

## 1. `-c copy` 的 `-to` 是封包层级，会多含一帧

`-ss A -to B -i IN -c copy` 直觉上应该只留 pts < B 的帧，实际上会**多含进 B 之后的第一个关键帧**。而那个关键帧十之八九正是下一个镜头的第一帧——于是每个复制段的结尾都挂着一帧杂镜头。

肉眼看是 1/30 秒的闪，逐帧扫描才抓得到。

**对策**：`cut.py` 的复制段结尾一律退 2 帧（`(b - 2) / fps`）。代价是每段少掉 2 帧，无感。

## 2. 段的**起点**只能落在关键帧上

`-c copy` 无法从 P 帧开始解码，所以起点会被吸附到最近的关键帧。三种情况：

- 关键帧刚好等于段首 → 完美，照抄。
- 关键帧在段首**之前** → 会把前一个镜头的尾巴带进来。
- 关键帧在段首**之后** → 干净，但段首那一截好画面就没了。

这就是 `hybrid` 模式存在的理由：段首到下一个关键帧之间那一小截单独重编码，接回照抄的部分。实测一支 320 秒的球赛片，`lossless` 少掉 13 秒画面，`hybrid` 只重压 4.9%。

顺带一提，剪辑软体输出的片子，关键帧常常**刚好**落在镜头切点上（编码器的 scenecut 侦测），所以运气好的时候大部分段都能直接照抄。先 `ffprobe -skip_frame nokey` 印出关键帧表对一下再决定模式。

## 3. 关键帧本身可能就是切镜的第一帧

段首对齐到关键帧，而那个关键帧是新镜头的第一帧——两者同时成立时，照抄就会漏一帧杂镜头进来。

**对策**：`detect.py --erode` 预设把每段头尾各削 1 帧当保险；`cut.py --tol-frames 0` 则不准为了迁就关键帧往前吃帧，强制走桥接重压。`--verify` 报出漏镜头时先试这个。

## 4. Otsu 单独用会太宽松

主机位的帧数量压倒性地多，距离直方图严重偏斜，Otsu 的谷底会被推得很高。实测那支球赛片 Otsu 给 24.2，结果把「整片纯色的赞助商转场卡」（距离约 20）也算成主机位。

**对策**：另外用主机位那一群自身的离散度算一个上界 `median + 8 × 1.4826 × MAD`，跟 Otsu 取较小者。宁可多剪，不要漏。

## 5. 取样率不能省

用 10fps 取样找切点，边界会有 ±0.1 秒误差，剪完接点上就挂着两三帧杂镜头。**一定要用原生 fps 逐帧跑**。320 秒的 720p 影片降采样成 64×36 只要几十秒，省不了多少时间，却会让整个结果不可信。

## 6. concat 出来的档案有重复时间戳

`-f concat -c copy` 接起来的档案，接点上会有两帧共用同一个时间戳，重新编码时会喷：

```
Application provided invalid, non monotonically increasing dts to muxer in stream 0
```

播放器（QuickTime／VLC）都正常播，是 B-frame 重排序造成的，**试过 `-fflags +genpts` 和 `-bsf:v setts` 都修不掉**（`setts` 用解码顺序 N 重算，遇到 B 帧反而更乱）。要根除只能全片重编码。

交付时主动讲这件事，别等用户自己撞到。

## 7. 重编码段的参数要跟原档对齐

不然 concat demuxer 会拒绝或产生怪东西。`cut.py` 从 `ffprobe` 读原档的 `profile`／`level`／`pix_fmt`／`time_base` 直接套用。音轨也要（44100／stereo／aac）。

## 8. zsh 与 ffmpeg 的两个小地雷

- `rm -f w_*.jpg` 在没有匹配档案时，zsh 会整行中止（`no matches found`），后面的指令不会跑。用子目录 + `rm -rf` 比较安全。
- ffmpeg 会吃掉 stdin，在 `while read` 回圈里跑会把回圈的输入吞光，第二圈就炸。**一律加 `-nostdin`**。
- 从 mp4 抽 jpg 遇到 `Non full-range YUV is non-standard` 而失败时，滤镜链补 `format=yuvj420p`。
