# 四种问法的解释骨架

SKILL.md 的四块结构（定义 → 机制 → 边界 → 例子）是共通骨架。实际进来的问法有四种，展开方式不同。

## 一、单一术语：「X 是什么」

照四块直接走。**边界那一块要写「它跟谁最容易搞混」**——那个最近的邻居概念就是轮 1 的干扰项来源。

## 二、关系：「X 跟 Y 差在哪」「X 和 Y 是什么关系」

不要写成两篇各自的解释再让使用者自己比。改成：

1. **各一句话定义**（各一句，不要各一段）
2. **它们在同一张图上的位置**：谁是谁的特例／上位／对立面／不同层级。**先讲清楚是哪一种关系，再讲差异**——「A 是 B 的一种」跟「A 与 B 互斥」会导向完全不同的题。
3. **最常见的混淆点**：大多数人把它们搞混时，是把哪一个的性质安到另一个身上
4. **一个能同时放进两者的例子**，指出在这个例子里两者分别扮演什么

出题时轮 1 直接考「这两个的关系是哪一种」，轮 3 给一个新场景问「这算 X 还是 Y」。

## 三、体系：「X 这一套是怎么运作的」

一整套东西（一个理论体系、一个技术栈、一套制度）不能用单一术语的骨架讲，会变成名词罗列。改成：

1. **先给地图**：这套东西由哪 3–5 个部件组成，一句话一个，说明**谁依赖谁**
2. **指出承重墙**：哪一个部件拿掉整套就垮。这是整段解释的重点，其余部件可以带过
3. **一条走通的路径**：从输入到输出实际走一遍，让部件之间的关系动起来
4. **这套东西在什么前提下才成立**

题目不要考「有哪几个部件」（那是背诵）。考**部件之间的依赖**：拿掉某一个会先坏掉哪里。

## 四、机制型：「为什么会 X」

1. **先讲结论的方向**（会变大还是变小、会稳还是会跑掉），再讲原因——不要把结论藏到最后
2. **因果链一条讲到底**，中间不跳步。跳掉的那一步通常就是使用者卡住的地方
3. **反事实**：如果链条中某一环反过来，结果会变成什么。← 轮 2 的边界题直接从这里出

## 共通的两条

**需要真实资料就去查。** 版本、数字、规格、谁提出的、目前主流做法——用 WebSearch／WebFetch 查过再写。整个 skill 的价值建立在讲的是对的；讲错了，后面四轮题只是把错误观念钉得更牢。

**默认 300–500 字，不写讲义。** 使用者说要深、或这是个体系型问题，才展开。解释太长会让检核循环变成附录，而检核循环才是这个 skill 的主体。
